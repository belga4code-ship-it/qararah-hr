# نظام الموارد البشرية لشركة قرارة

تطبيق Next.js بواجهة عربية RTL، وقاعدة بيانات Supabase. يتضمن تسجيل الدخول، لوحة معلومات من بيانات قاعدة Supabase، وصفحة موظفين مع معاينة واستيراد ملف Excel.

## التشغيل المحلي

```bash
npm install
npm run dev
```

افتح `http://localhost:3000`.

## إعداد Supabase

1. أنشئ مشروع Supabase للشركة.
2. انسخ `.env.example` إلى `.env.local` وأضف رابط المشروع ومفتاح `Publishable`.
3. نفّذ `supabase/schema.sql` من SQL Editor في لوحة Supabase مرة واحدة.
4. نفّذ `supabase/migrations/20261008_employee_roster.sql` لتجهيز استيراد سجل الموظفين الحالي.
5. نفّذ `supabase/migrations/20261012_hr_event_types.sql` ثم `supabase/migrations/20261013_hr_effects_workflow.sql` لتفعيل المؤثرات الأسبوعية وصلاحياتها.
6. أنشئ حسابات المستخدمين من Supabase Auth، ثم أضف ملفاتهم إلى جدول `profiles` مع الأدوار والفروع.
7. لتمكين الموظف من تقديم الطلبات، اربط حسابه بسجل الموظف عبر `profiles.employee_id`، مع وضع `branch_id` الصحيح. هذا الربط مطلوب لكل موظف.

لا تضع `service_role` في متغير يبدأ بـ `NEXT_PUBLIC_` أو في أي كود يعمل بالمتصفح.

## وحدات البيانات الحالية

- الفروع والأقسام والمسميات الوظيفية وملفات الموظفين.
- الورديات ومعرّف الموظف في جهاز ZKT.
- دفعات استيراد الحضور وسجلات البصمة والاستثناءات.
- المؤثرات الوظيفية مثل الإجازات والمأموريات والخصومات والنقل ونهاية الخدمة.
- تقييمات الأداء وبنود التقييم.

## استيراد الموظفين

من صفحة الموظفين اختر استيراد موظفين، ثم حمّل ملف `.xlsx` الذي يحتوي على ورقة `DATA BAISE 2026`. راجع المعاينة قبل الحفظ. تُحفظ جميع أعمدة الورقة: بيانات العمل في الجداول الأساسية، والبيانات الشخصية والمالية في `employee_private`، مع نسخة المصدر في `employee_private.source_data`. تظل البيانات الخاصة مقيدة بسياسات RLS لأدوار الموارد البشرية والمدير. الحالات غير المحددة تُحفظ للمراجعة، ولا تُصنف نشطة تلقائيًا.

## المؤثرات الأسبوعية

- الموظف يقدم طلب إجازة أو إذن تأخير أو استئذان أو مأمورية؛ الطلبات تبدأ بحالة «قيد المراجعة».
- مدير الفرع يضيف موظفًا جديدًا أو يسجل إنهاء خدمة لموظف في فرعه، ويرفع طلب خصم للإدارة الرئيسية.
- الإدارة الرئيسية تعتمد أو ترفض الطلبات مع سبب إلزامي، ويمكنها تسجيل خصم مباشر. الخصومات المعتمدة تُحفظ في سجل خصومات الرواتب؛ احتساب صافي الراتب يحتاج وحدة مسير رواتب مستقلة.

## موافقات الطلبات الفردية

طبّق `supabase/migrations/20261105_individual_request_approvals.sql` بعد التحديثات السابقة. الإجازة وإذن الخروج وإذن التأخير تبقى معلقة حتى يعتمد كل مسؤول معيّن عند تقديم الطلب، ويمكنهم الاعتماد بأي ترتيب. صلاحية `effects.approve` لا تتجاوز الموافقات؛ مدير النظام وحده يستطيع اعتماد الطلب نهائيًا مع تسجيل التجاوز دون نسبة موافقة للمسؤولين الآخرين. يُسجّل الرفض وينهي الطلب.

التحديث يحول الطلبات المعلقة إلى موافقات فردية ويحفظ القرارات المسجلة. الطلبات المكتملة لا تُفتح تلقائيًا؛ مجلد `supabase/repairs` يحتوي إصلاحًا مخصصًا لحالة يوسف المذكورة في المراجعة، يحفظ موافقة أحمد ويعيد انتظار خالد، ويرفض التنفيذ إذا تغيّر الطلب أو ارتبط بخصم مالي.

شغّل `npm run test:approvals` لاختبار التحديث بقاعدة PostgreSQL معزولة دون الاتصال ببيانات الشركة.

## تصحيح سجلات التقرير

طبّق `supabase/migrations/20261106_admin_report_corrections.sql` لتمكين زر التعديل في تقرير الإذونات والخصومات. التعديل متاح لمدير النظام فقط، ويتطلب سببًا، ويُوثّق المبلغ والتواريخ والسبب قبل التغيير وبعده في `audit_log`، مع منفذ التعديل ووقته. لا يغيّر الموظف أو نوع الطلب أو حالة الموافقات. يتحدث المبلغ المسجل ضمن خصومات الراتب عند تصحيحه، مع منع الحفظ إذا تغير إصدار السجل أو حالته بعد فتحه.

## تعديل الأهداف وحذف الأهداف الخاطئة

تعرض صفحة «أهدافي» سجلًا شهريًا بملخص الإنجاز وبحث بالهدف أو الموظف أو الكود الوظيفي، مع فلاتر الفرع والحالة. تتم الإضافة من نافذة فيها بحث بالاسم أو الرقم الوظيفي وفلاتر للفرع والقسم لاختيار الموظف؛ تتبع قائمة الأقسام الفرع المختار مع إظهار عدد النتائج وإتاحة مسح الفلاتر. تُعرض تفاصيل الهدف وتسجيل الإنجاز في نافذتين مستقلتين. تظهر الأهداف التي لم يسجل إنجازها بحالة «بانتظار التقييم» دون احتسابها صفرًا في متوسط الإنجاز.

تعرض خانة الإنجاز القيمة المحققة ونسبتها من المستهدف، مع معاينة مباشرة للنسبة والمتبقي أثناء الإدخال. تحسب النسبة بقسمة الإنجاز الفعلي على المستهدف وضربه في 100، وتسمح بتجاوز 100٪؛ المستهدف الصفري أو غير المحدد لا ينتج نسبة مئوية.

طبّق `supabase/migrations/20261107_employee_goal_corrections.sql` لإتاحة تعديل اسم الهدف وتفاصيله وشهره وقيمته المستهدفة ووحدته، أو حذفه من القوائم. التعديل والحذف حصريان لدورَي مدير النظام (`admin`) ومدير الموارد البشرية (`hr`)، بما يشمل الأدوار الإضافية؛ صلاحية `goals.manage` وحدها لا تمنحهما. حذف الهدف يؤرشفه ويحفظ إنجازه وسجل التدقيق، دون المساس بالتقييمات الشهرية المستقلة. التعديل يتطلب سببًا ويحافظ على الإنجاز الفعلي، ويُرفض إذا تغير الهدف أو إنجازه بعد فتح نافذة التعديل. اختبارات الحماية والتدقيق: `npm run test:goals`.

## شاشة تقييم الأداء

تعرض الشاشة سجل الموظفين مع البحث بالاسم أو الرقم الوظيفي وفلاتر الشهر والفرع والقسم وحالة التقييم. يفتح زر «تقييم» نافذة للأسئلة والملاحظات مع تحديث مجموع النقاط والنسبة أثناء الإجابة، ويفتح زر «المقيّمون» نافذة إسناد منفصلة قابلة للبحث. تحفظ النوافذ عبر دوال التقييم والإسناد الحالية حسب الصلاحيات؛ تُهيّأ الإجابات من تقييم المستخدم للشهر المحدد عند كل فتح. يُحسب المتوسط من نسب التقييمات المقدمة، ويظل حاليًا إلى أن يقدم كل مقيّم مسند تقييمه؛ تقييم إضافي لا يغني عن مسؤول مسند لم يقيّم.
