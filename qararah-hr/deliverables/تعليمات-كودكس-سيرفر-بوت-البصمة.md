# مهمة كودكس على سيرفر البصمة: تشغيل ومراجعة بوت مزامنة قرارة HR

## المطلوب

راجع وشغّل حزمة مزامنة ZKBio الموجودة في الملف المضغوط:

`qararah-zkbio-sync-windows-v0.2.2-2026-10-31.zip`

هدفها قراءة حركات الحضور من ZKBio Time وإرسالها لاحقًا إلى وظيفة Supabase Edge Function، كل 15 دقيقة، مع منع التكرار وحفظ آخر نافذة ناجحة.

ابدأ بالفحص والتشغيل التجريبي فقط. إذا وجدت مشكلة في الاتصال أو أسماء الحقول أو صيغة الرد، أصلح إعدادات الخدمة أو كودها داخل نسخة العمل، ثم أبلغني بما تغير. لا تثبّت مهمة Windows ولا تحول إلى الإرسال قبل نجاح فحص القراءة التجريبي.

## معلومات ZKBio التي تم التأكد منها على السيرفر

- البرنامج: ZKBio Time **9.0.6 (Build 20260112.21755)**.
- عنوانه المحلي على السيرفر: `http://127.0.0.1:8089`.
- API تسجيل الدخول: `POST /api-token-auth/`، والرد أعاد حقل `token` أثناء الفحص.
- قائمة الأجهزة: `GET /iclock/api/terminals/`.
- الحركات: `GET /iclock/api/transactions/`.
- مصادقة الطلبات: `Authorization: Token <token>`.
- فلاتر الحركات التي نجحت: `start_time`, `end_time`, `emp_code`, `terminal_sn`, `terminal_alias`.
- الصفحات: اتبع `next` إلى أن تكون قيمته `null`.
- تجربة القراءة السابقة رجّعت 72 حركة ليوم 31 أكتوبر 2026، والصفحة الثانية نجحت.
- هناك 7 أجهزة. لا تستنتج معنى رموز الحالة 1 و3؛ خزّنها كما وردت فقط.

معلومات الأجهزة، للتطابق الإداري فقط:

## خطوات العمل

1. فك الحزمة في مجلد عمل على السيرفر، وراجع `services/zkbio-sync/README.md`.
2. تحقق أن Node.js **24.19 أو أحدث** متوفر. السيرفر أبلغ سابقًا أن لديه Node.js 24.19.0.
3. أنشئ `services/zkbio-sync/.env` من `.env.example`، واملأ بيانات دخول ZKBio محليًا. لا تطبع الأسرار في سجل الطرفية، ولا ترسلها في تقرير أو محادثة.
4. اترك `SYNC_MODE=dry-run`. اختر `SYNC_INITIAL_FROM` محدودًا، مثل بداية يوم واحد أو أسبوع متفق عليه، كي لا تبدأ قراءة كل التاريخ.
5. شغّل من مجلد الخدمة:

   ```powershell
   npm run live:validate
   npm run live:once
   ```

6. راجع أسماء الحقول التي يعرضها dry-run. أسماء المسارات و`emp_code` و`next` تم اختبارها؛ أما أسماء حقول معرّف الحركة ووقت البصمة ونوعها وبيانات الجهاز فلم تُثبت بعد. إذا اختلفت، عدّل متغيرات `ZKBIO_*_FIELD` في `.env`، أو أصلح الـmapper بأقل تعديل ممكن. لا تطبع بيانات الموظفين أو حمولة السجلات كاملة.
7. تأكد أن كل الصفحات تُقرأ، وأن الوقت المحلي يُحوّل باستخدام `Africa/Tripoli`، وأن المزامنة لا تتقدم بمؤشرها في وضع dry-run.
8. راجع معي نتيجة الفحص قبل تثبيت المهمة أو تفعيل `SYNC_MODE=push`.

## Supabase والأمان

- لا تستخدم مشروع Supabase الإنتاجي في الاختبار، ولا تطبق migration عليه.
- لا تضع `SUPABASE_SERVICE_ROLE_KEY` على سيرفر Windows؛ هذا المفتاح مكانه أسرار Edge Function على Supabase فقط.
- الحزمة تحتوي مسودة migration ووظيفة استقبال: `supabase/migrations/20261031_zkbio_attendance_ingest.sql` و`supabase/functions/zkbio-attendance-ingest/index.ts`.
- لا تنشرهما ولا تطبقهما إلا على مشروع Supabase تجريبي منفصل، وبعد مراجعتي.
- لا تشغّل مهمة Windows المجدولة حتى ينجح اختبار staging اليدوي. سكربت التثبيت يرفض وضع dry-run عمدًا؛ لا تتحايل على هذا الفحص.
- لا تغير أجهزة ZKTeco ولا قاعدة ZKBio الداخلية ولا جداول `attendance_records`. وظيفة البوت حفظ الحركات الخام فقط؛ حساب التأخير والحضور اليومي يبقى كما هو إلى أن نتحقق من القواعد.
- يجب أن تبقى السجلات التي لا تطابق `employees.zkt_user_id` محفوظة وغير مرتبطة بموظف للمراجعة، ولا تحذفها.
- لا تشارك ملف `.env` أو قيمه. لا تضعه ضمن ZIP أو Git.

## ما أحتاجه في تقريرك

- إصدار Node الفعلي ونجاح/فشل الاتصال بـZKBio (من دون أي كلمة مرور أو token).
- أسماء مفاتيح استجابة الحركات والأجهزة فقط، لا ترسل أسماء موظفين أو حمولات شخصية.
- عدد الأجهزة والحركات والصفحات المقروءة والفترة التي اختبرتها.
- إعدادات `ZKBIO_*_FIELD` التي تطلب تعديلها وسبب كل تعديل.
- أي خطأ مختصر بعد إزالة الأسرار والبيانات الشخصية.
- تأكيد صريح أن الاختبار بقي dry-run ولم يكتب إلى Supabase ولم يثبت Task Scheduler.

إذا احتجت إصلاحًا، عدّل نسخة العمل محليًا على السيرفر وأرسل لي ملخص التغيير والملفات المعدلة. لا ترسل أسرار الدخول.
